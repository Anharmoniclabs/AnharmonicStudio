# Building Anharmonic Studio from source

This guide is for developers maintaining their own toolchain and runtime environment.
For the musician-facing distribution, use the [official download page](https://anharmoniclabs.github.io/AnharmonicStudio/#download).
Unsigned release-candidate installers for Linux, Windows, Intel Mac, and Apple Silicon
Mac are available for $1 USD once, plus applicable tax. Their source remains free.

The complete application source and build/installation scripts are free under
GPL-3.0-or-later. You may build and modify them without purchasing a package.
**We do not provide installation or configuration troubleshooting for self-compiled
copies.** Developers are responsible for their dependencies, audio configuration,
and local validation. Reproducible application bug reports and patches are welcome;
see [SUPPORT.md](SUPPORT.md).

A source checkout is a developer build, not a signed installer or a managed update
channel. Compatibility with arbitrary operating-system, driver, and dependency
combinations is not guaranteed. There are no artificial build restrictions or
activation requirements.

## Source and build components

The same portable C++17 core in `mpclab/native/` is compiled for Windows x64,
Linux x64, Intel Mac, and Apple Silicon Mac. `scripts/build_native.py` builds the
library used by the application; `native/CMakeLists.txt` independently builds
that same source and its device-free C++ tests. Neither production build needs
ALSA, Lilv, or a platform-specific plugin SDK.

The device callback is a C++ function pointer passed directly to PortAudio.
Sample playback, synth kernels, convolution, compression, limiting, delay,
reverb, and track gain/meter kernels run in C++. Python retains the Qt UI,
project model, musical scheduling, and isolated plugin orchestration on a
render worker. The bounded two-block worker queue is included in reported
output latency. This is a hybrid migration; it is not an entirely C++ musical
scheduler and it does not eliminate producer starvation under arbitrary load.

The historical `native/src/` ALSA/LV2 prototype is opt-in with
`-DANHARMONIC_BUILD_LEGACY_LV2=ON`; it is not selected by the desktop application.

| Component | Build input |
| --- | --- |
| Python/Qt/audio dependencies | `pyproject.toml`, `uv.lock`, Python 3.12 |
| Active native DSP | `mpclab/native/*.cpp`, `mpclab/native/core.hpp`, `mpclab/native_dsp.py`, `scripts/build_native.py` |
| Frozen executable and bundled dependencies | `scripts/frozen_entry.py`, `scripts/build_release.py`, `requirements-build.txt` |
| Windows setup EXE and uninstaller | Inno Setup script generated by `package_windows()` in `scripts/build_release.py` |
| macOS .app and DMG | PyInstaller BUNDLE/Info.plist and hdiutil steps in `scripts/build_release.py` |
| Linux archive and per-user install | `scripts/build_release.py`, `mpclab/install_bundle.py` |
| Exact source archive | `scripts/build_source_bundle.py` |
| Native runner environment and checks | `.github/workflows/release-candidates.yml` |

The generated platform packaging definitions are included in the common build script;
there are no missing private wrapper scripts or separate proprietary platform source
trees. A signing identity, notarization account, or private encryption key is not
required to build an unsigned local package.

## 1. Prepare your platform

Install Git, [uv](https://docs.astral.sh/uv/getting-started/installation/), a Python 3.12
runtime, FFmpeg with ffprobe, and the platform's compiler/runtime prerequisites.
The locked environment also installs python-rtmidi and Pedalboard for MIDI/plugin
hosting. Third-party plugins are separate installs and must match your OS and CPU.
Use the locked dependency versions for the checkout being built. Initial dependency
installation requires network access.

### Linux x86_64

Provide a C++17 compiler, Qt graphics libraries, PortAudio, and libsndfile. On Debian/Ubuntu:

```sh
sudo apt-get update
sudo apt-get install build-essential git ffmpeg libegl1 libgl1 libopengl0 libxkbcommon0 libportaudio2 libsndfile1
```

Install uv and Python 3.12 separately. Other distributions require their equivalent
packages and a working desktop/audio stack. Official Linux candidates are compiled
on Ubuntu 22.04; building on a newer distribution can raise the minimum runtime
requirements of the package you produce.

The historical ALSA/LV2 prototype additionally requires pkg-config, PortAudio
and ALSA development headers, and Lilv development files. These are not required
for the production C++ core.

### Shared engine source

All platform builds preserve the `mpclab.engine.Engine` control API. Its
render worker owns musical state and calls the portable native kernels.
`native_output.py` owns the worker/stream lifetime; `native/output.cpp` owns the
single-producer/single-consumer FIFO and device callback. The callback never
acquires the Python GIL, allocates, waits on a mutex, loads media, or calls a
plugin. On starvation it writes silence and increments an observable counter.
Stopping joins the producer and closes PortAudio before releasing native memory.

`sample_voice.py` preserves voice articulation and its Python reference path;
`engine_scheduling.py` collects musical events; `engine_mixing.py` coordinates
the render graph; and `engine_offline.py` exports through the same DSP kernels.
`MPC_NATIVE_DSP=0` selects the reference backend for regression comparisons.
Release self-checks reject packages missing the compiled core or output callback.

The default stream queue adds two configured audio blocks of buffering. It is
reported by `Engine.latency_ms`; it must not be presented as zero added latency.
CPU benchmarks measure render work, not physical round-trip latency. Hardware
acceptance and signing/notarization remain separate release requirements.

### macOS — Apple Silicon or Intel

Install Apple's Xcode command-line tools, Git, uv, Python 3.12, FFmpeg/ffprobe,
and PortAudio. The native build jobs provision the media/audio dependencies with:

```sh
brew install ffmpeg portaudio
```

Use a native terminal and a matching Python architecture. Build Apple Silicon and
Intel packages on their respective architectures; a DMG built for one is not a
universal app. `c++` must resolve to a working Apple Clang toolchain. DMG creation
uses the system `hdiutil` utility.

### Windows x86_64

Install Git, uv, Python 3.12 x64, FFmpeg/ffprobe, and Visual Studio Build Tools with
the C++ toolchain, Windows SDK, and Clang tools. Use a Developer PowerShell/Command
Prompt configured for x64 so Clang can find the Microsoft headers and linker libraries.
`clang++`, `ffmpeg`, and `ffprobe` must be on PATH.

The build uses Clang for the native DLL; installing a Python interpreter alone is
not enough. For a setup EXE, also install Inno Setup 6. The tested CI environment is
recorded in `.github/workflows/release-candidates.yml`, including its compiler
initialization and FFmpeg executable-directory handling.

## 2. Get the matching source

```sh
git clone https://github.com/Anharmoniclabs/AnharmonicStudio.git
cd AnharmonicStudio
```

For a particular official build, use its accompanying source ZIP or check out the
`source_commit` recorded in its `build-info.json`. A newer default-branch checkout
is not necessarily the corresponding source for an older installer. Preserve
`LICENSE`, `THIRD_PARTY.md`, and the included asset/dependency notices.

## 3. Install the locked environment and compile native DSP

From the repository root, in the prepared native environment:

```sh
uv sync --locked --group dev
uv run --no-sync python scripts/build_native.py
```

The native helper is built under `.native/`. Source and compiler flags determine its
cache name; failed builds do not replace an existing working library. Investigate
compiler failures before using a package as a release candidate.

## 4. Validate before opening a working session

```sh
uv run --no-sync python -m mpclab --self-check
uv run --no-sync python -m pytest -q tests/test_native_dsp.py tests/test_release_runtime.py tests/test_vocal_workspace.py
```

The self-check creates a disposable offscreen session, loads the native DSP, renders
the UI, saves/reopens a project, exports through a subprocess, and checks FFmpeg.
It does not open an audio device. Full test and benchmark configuration is in
`.github/workflows/quality.yml`; native cross-platform regression selection is in
`.github/workflows/release-candidates.yml`.

For Linux development, `uv run --no-sync python scripts/run_tests.py -- -q` runs
the full suite with a memory ceiling. `bash scripts/quality.sh` also runs lint, formatting, Python DSP
fallback checks, and callback benchmarks. Hardware acceptance is separate. Test with
an isolated library and disposable projects, not valuable recordings.

## 5. Run and configure your developer build

```sh
uv run --no-sync python -m mpclab --data-dir /path/to/developer-session
```

Use a platform-appropriate absolute data path; on Windows, quote paths containing
spaces. Configure your input/output devices, operating-system permissions, and audio
backend in Audio setup. Start with 48 kHz and a 512-frame buffer, then measure before
reducing buffer sizes. Device/driver behavior remains your responsibility in a
self-built copy.

Linux developers can use `./run.sh` after completing the dependency, native compilation,
and validation steps above. It launches the existing `.venv` only; it does not install
dependencies, create an environment, or compile code. After changing native source,
explicitly rerun `scripts/build_native.py`. The Python DSP fallback remains available
for development and can require more buffer headroom.

Optional neural stem separation needs additional dependencies and model downloads.
The Linux developer helper is `./install-separation.sh`. It is not bundled in these
release candidates. To build the separate Linux C++ engine, use `bash scripts/build-native.sh`
after installing its additional development dependencies.

If saving a recording fails, use **Retry save** in Song or **Retry save take** in the
vocal editor. Recovery WAVs remain under the session's `projects/recordings/` until
saved or explicitly discarded. Keep the session library with its projects.

Project format 5 persists unique mixer track IDs. Older formats migrate in memory
using repeatable IDs for the original eight slots; names, effects and integer
routing stay intact. IDs survive save/reopen and undo snapshots. This foundation
does not enable adding, deleting or reordering mixer channels. Earlier builds
supporting format 4 reject newly saved format-5 projects, so keep original project
copies when testing across versions.

## 6. Produce an unsigned native package

Build on the target OS and architecture. Packaging is a separate step from running
source and requires the build dependencies above:

```sh
uv pip install -r requirements-build.txt
uv run --no-sync python scripts/build_release.py dist/my-candidate --version 0.1.0-rc.1
```

The output directory must not already exist. The script packages the native app,
checks relocation and platform installation where supported, and includes matching
source, notices, metadata, and checksums. It does not apply commercial code signing
or notarization. See [packaging/RELEASE.md](packaging/RELEASE.md) for the exact checks
and [DISTRIBUTION.md](DISTRIBUTION.md) for official delivery requirements.

Create a standalone source archive with:

```sh
uv run --no-sync python scripts/build_source_bundle.py dist/AnharmonicStudio-source.zip
```
